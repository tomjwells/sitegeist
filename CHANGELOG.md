- **🔊 Read aloud on every answer** (Tom, 2026-11-07: "Add a small 🔊 read aloud button to the sitegeist panel, using the new speak TTS service"). A speaker button next to the copy button on each assistant message: click to play, click again to stop, a spinner while the audio renders; only one answer plays at a time; switching chat stops it. Uses main-pi's speak service (`POST /v1/audio/speech`, `prepare: true`, mp3), default `http://speak.tjwpier:8610`.
  - `src/speak/chunk.ts`: the message's Markdown is split at block boundaries (blank lines; code blocks, tables and lists stay whole) and packed into chunks. Targets ramp 120 → 250 → 500 → 800 characters. Measured on the M4 with the model loaded: speech ~10 chars/s, rendering ~20-23 chars/s (149 chars → 13.1 s of audio in 7.4 s; 665 → 65.4 s in 28.4 s), so an 800-character first chunk would mean ~35 s of silence; 120 starts in ~6 s, and each target is about twice the previous one, so the next chunk renders while the current one plays. Only a paragraph is ever cut inside, at sentence ends (an opening paragraph over 1.5× the first target, first piece at least half of it); nothing exceeds 4,000 characters (speak's limit is 5,000 after prepare).
  - `src/speak/speak-player.ts`: one audio element; chunk 1 plays as soon as it arrives, the next two are fetched one after another while it plays (one request to speak at a time; with only the next one fetched, a long chunk after a short one left 10 s of silence in Tom's Zen); fetched audio stays in memory per voice + message (newest 40), so a replay is instant; requests still running at Stop finish into the cache. No retries: 503 or no answer → "speak is offline (M4 asleep?)" next to the button; 413/422/other get short notes. The voice is the agent's own name when `/v1/voices` lists it (main-pi's panel id `prime` → `main-pi`), else `main-pi`. Never logs the text.
  - `src/speak/speak-client.ts`: zod on every JSON reply (`/v1/voices`, `/health`, OpenAI-style errors); every request bounded (6 s small calls, 180 s per chunk). Settings → **Read aloud** (`src/dialogs/SpeakTab.ts`): on/off switch, speak URL, Test button. Tooltip: "Read aloud · Built with Fish Audio" (Fish Audio Community License).
  - Panel diagnostic `sitegeist_speak` (relay browser call, not an agent tool): `status` (player state, no text), `click` (press the Nth answer's 🔊, same path as a click), `stop`, so main-pi can check playback in Tom's real browser.
  - `browser_tabs` now also applies `query` in the panel: a raw relay call with a query used to get every tab back (main-pi then closed all of Tom's Zen tabs while cleaning up its probe tabs; restored).
  - Tests: `test:speak` (chunking, voice choice, client against a stand-in speak: audio, 503/413/422/502, nothing listening; 6/6) and `test:speak:extension` (real extension, stand-in relay + stand-in speak with no CORS headers and real ffmpeg mp3s: spinner, playing with currentTime advancing, prefetch while playing, every chunk played in order and the requests equal `chunkMarkdown(message)`, replay with no request, stop, 503 → note after one request, settings switch hides the buttons; screenshots `tests/.out/speak-*.png`). zod is now a direct dependency (same 4.5.4 already installed via pi-ai).

### Fixed

- **`browser_download` with `code` failed for every return type in Zen's default (isolated) world, and page-script errors came back without their message** (Jennifer request 502b1bb0, 2026-11-07, DPD confirmation page: "can't access property \"slice\", JSON.stringify(...) is undefined"; the same code with `world: "main"` worked). Two Firefox-only causes, reproduced in real Zen 1.23.2b:
  - The base64 step `String.fromCharCode.apply(null, typedArray.subarray(...))` throws "Permission denied to access property constructor" in Firefox's isolated world. The in-page helper now uses `FileReader.readAsDataURL` (native base64; 3 MB in 14 ms; works in both worlds and in Chrome).
  - Firefox hands a thrown `Error` back from `userScripts.execute` as `error: {}`, and Chrome drops a thrown string. `runUserScript` only accepted a string error, so the error became `result: undefined`: the download crashed on `JSON.stringify(undefined).slice` and `browser_eval` printed a silent `null`. The wrapper now returns page errors as a tagged result that `runWithTimeout` turns back into the real message, so `browser_eval`, `browser_eval` with `urls` and `browser_download` report it in both browsers. Any non-empty `error` value from the browser is also treated as an error.
  - Test: `assertDownloadsAndPageErrors` in `tests/prime-relay.fixture.ts`, run through the stand-in relay in both `test:split:extension` (Chrome) and `test:firefox:extension` (Zen): isolated `{mime, base64}`, Blob, UTF-8 string, `url` fetch, main world, `return undefined` reports "got undefined", and a thrown Error keeps its message in both worlds. Zen test 3 ("a chat open in another window's sidebar") is flaky without this change too (1 of 3 baseline runs).

- **Every browser call answers before the relay gives up** (2026-11-02: three calls into a LinkedIn tab waited 35 s each and came back as a bare `browser_call_timeout`; 49 such timeouts since September). `handleBrowserCallBounded` caps each call inside the extension (page-script tools: their own `timeoutMs` + 3 s; navigate 55 s; screenshot 15 s; the rest 10 s; no cap for `browser_eval` across `urls`) and answers with what the agent needs: `browser_page did not finish in 18 s inside the browser (tab 121 "Tomos Wells | LinkedIn" https://…; status complete; unloaded (discarded))` plus what works instead (browser_screenshot needs no page script; browser_navigate reloads; ask Tom to click the tab). An unloaded tab (Zen's tab unloader, Chrome's Memory Saver) is reloaded before a page call, the way the browser does when Tom clicks it (`wakeIfDiscarded`, bounded 15 s). The cancel after an eval timeout is bounded too (2 s) - when the page ran no script at all it hung as well, so no reply ever went out. `browser_tabs` details carry `discarded` and `status`.
- **A new R730 chat could vanish from the list** (Tom, 2026-10-25: a Jennifer chat about whey "has disappeared"). - **Attachments on an unsent message were lost when switching tabs** (Tom, 2026-10-24: "If I try to attach things, then change the browser tab, it reloads but loses the attachments" - as he was typing, not sent yet). Switching to a page that has its own chat reloads the panel onto that chat. The typed text came back (it is saved as a draft on every keystroke); the files were not part of the draft. - **A message that did not reach the R730 looked sent, and a resend could run the task twice** (Tom, 2026-10-18, on a train: his "Sources page" message to Sed Coach showed twice in the chat; the R730 had it once and Sed Coach had built the page, but the panel's connection was down, so the reply never arrived and the second copy never left the browser).
  - A user message is now shown at once and marked: "Sending…" while the POST is in flight; "Not sent (reason). It goes out when the connection is back." with **Retry now** and **Discard** when it failed (no connection, timeout, relay error). The header shows "N unsent".
